# 会议室预定并发说明

> 本文档解释 `UserServiceImpl.bookMeeting` 中 synchronized + TransactionTemplate 的设计意图与局限性。
>
> 代码依据：`UserServiceImpl.java`、`UserController.java`、`HytzMapper.xml`、`MeetingRoomBookingTest.java`。

---

## 1. 业务流程

```
POST /user/kh
    ↓
UserController.kh()
    ↓ 解析时间、用户列表
    ↓
UserService.bookMeeting(hysbh, hynr, ksTime, jsTime, userIdList, operatorId)
    ↓
    ├─ 1. validateBookingParams()          ← 参数校验（无需锁/事务）
    │     - ksTime < jsTime
    │     - hysbh 非空
    │     - userIdList 非空
    │
    ├─ 2. synchronized (bookingLock) {     ← 加 JVM 对象锁
    │     TransactionTemplate.execute {     ← 开启事务
    │
    │       ① 校验所有用户存在
    │       ② countOverlappingReservations  ← 查该会议室时间冲突数
    │       ③ countUserConflicts (per user) ← 查每个参会人日程冲突
    │       ④ insertReservation (per user)  ← 为每个参会人插入 hytz 记录
    │       ⑤ updateHys                     ← 更新会议室状态
    │
    │       return result                   ← 事务提交（在锁内）
    │     }
    │   }                                   ← 释放锁
    ↓
    ├─ 3. 发送短信通知（逐人调用 smschinese.cn）
```

## 2. 为什么 synchronized 要包裹事务提交

### 2.1 核心问题：TOCTOU 竞争

如果不加锁，两个线程可能同时执行到 `countOverlappingReservations`，都读到 0（无冲突），然后都执行 `insertReservation`，导致同一会议室同一时段被重复预约。

```
线程A: SELECT COUNT(*) = 0   (检查)
线程B: SELECT COUNT(*) = 0   (检查)
线程A: INSERT INTO hytz ...  (写入)
线程B: INSERT INTO hytz ...  (写入) ← 冲突！两次都成功了
```

这就是经典的 **Time-of-check to Time-of-use (TOCTOU)** 问题。

### 2.2 为什么不能把事务放在 synchronized 外面

如果先开事务、再加锁、再提交：

```java
// 错误示范（伪代码）
@Transactional           // ← 事务在方法入口开启
public Map bookMeeting() {
    synchronized(lock) { // ← 锁只保护方法体
        // ... 业务逻辑
    }
    // 事务在方法返回后由 Spring AOP 代理提交 ← 此时锁已释放！
}
```

问题在于：Spring 的 `@Transactional` 是基于 AOP 代理实现的，事务的 commit 发生在代理层（方法返回之后），而 synchronized 在方法体结束时就已释放。这意味着：

```
线程A: 获取锁 → 执行SQL → 释放锁 → (事务尚未提交)
线程B: 获取锁 → SELECT COUNT(*) = 0  ← 读到的是线程A尚未提交前的旧数据！
线程A: (事务提交)
线程B: INSERT → 冲突
```

### 2.3 正确做法：TransactionTemplate 手动控制

```java
synchronized (bookingLock) {                    // ① 获取锁
    TransactionTemplate txTemplate = new TransactionTemplate(transactionManager);
    return txTemplate.execute(status -> {       // ② 开启事务
        // ... 检查 + 写入
        return result;                          // ③ 事务提交（在锁内！）
    });
}                                               // ④ 释放锁（事务已提交）
```

保证顺序：

```
线程A: 获取锁 → 开启事务 → 检查+写入 → 事务提交 → 释放锁
线程B: 等待锁...
线程B:        获取锁 → 开启事务 → SELECT COUNT(*) > 0 → 返回失败 → 释放锁
```

### 2.4 验证：MeetingRoomBookingTest.testConcurrentBooking

```java
// 两个线程同时预约 C303 同一时段
Thread t1 → bookMeeting("C303", "并发会议1", ks, js, userIds(1L), 1)
Thread t2 → bookMeeting("C303", "并发会议2", ks, js, userIds(3L), 1)

// 使用 CountDownLatch 确保两线程同时起跑
// 断言：恰好成功 1 次，失败 1 次
assertEquals(1, successCount.get());
assertEquals(1, failCount.get());
```

此测试验证了 synchronized 锁的有效性。

## 3. 冲突检测 SQL 语义

### 3.1 会议室时间冲突

```sql
SELECT COUNT(*) FROM hytz
WHERE hydd = #{hydd}            -- 同一会议室
  AND ksTime < #{jsTime}        -- 已有预约的开始 < 新预约的结束
  AND jsTime > #{ksTime}        -- 已有预约的结束 > 新预约的开始
```

**重叠判断使用严格不等式**：`A_start < B_end AND A_end > B_start`

这意味着：
- `A_end == B_start`（相邻）**不算冲突** → 允许背靠背预约
- 部分重叠、完全包含、完全相同 → 均判定为冲突

### 3.2 用户日程冲突

```sql
SELECT COUNT(*) FROM hytz
WHERE hybtzr = #{userId}        -- 同一用户
  AND ksTime < #{jsTime}
  AND jsTime > #{ksTime}
```

同一用户在不同会议室的同一时段也会冲突——一个人不能同时参加两个会。

## 5. 并发设计的局限性

### 5.1 单 JVM 局限

```
                    ┌─────────────────┐
                    │   JVM 实例 A     │
                    │                 │
                    │  bookingLock    │ ← synchronized 只对当前 JVM 内的线程有效
                    │  (Object 锁)    │
                    └─────────────────┘

                    ┌─────────────────┐
                    │   JVM 实例 B     │
                    │                 │
                    │  bookingLock    │ ← 另一个 JVM 有自己的锁对象，互不互斥！
                    │  (另一个 Object) │
                    └─────────────────┘
```

**`synchronized(bookingLock)` 是 JVM 进程内的对象锁**，只在单 JVM 内有效。如果部署多实例（Nginx 负载均衡 / 多 Pod），两个实例各自持有独立的锁对象，TOCTOU 竞争会再次出现。

### 5.2 升级到分布式锁的方案（如需）

| 方案 | 原理 | 适用场景 |
|------|------|----------|
| **数据库唯一约束** | 在 `hytz` 表上增加 `(hydd, ksTime, jsTime)` 的组合约束或区间排他约束 | 最简单，但 MySQL 不支持区间排他约束，需要应用层配合 |
| **MySQL `SELECT ... FOR UPDATE`** | 对会议室行加行锁，锁在事务提交后释放 | 需要 `hys` 表中有可锁定的行记录 |
| **Redis 分布式锁** | `SET lock:room:{hysbh} {uuid} NX EX 30` | 多 JVM 部署，需引入 Redis 依赖 |
| **数据库乐观锁** | 在 `hys` 表加 `version` 字段，UPDATE 时 `WHERE version=?` | 需修改表结构 |

### 5.3 其他局限

| 问题 | 说明 |
|------|------|
| **锁粒度粗** | `bookingLock` 是全局唯一的 Object 锁，所有会议室的预约都串行化。即使预约不同房间也要排队。理想做法是按 `hysbh` 分段锁。 |
| **锁超时缺失** | synchronized 没有超时机制，如果事务因数据库连接池耗尽而阻塞，线程将无限等待。 |
| **短信发送在锁外** | `UserController.kh()` 中短信发送在 `bookMeeting` 返回后执行，不在事务和锁的保护范围内。短信发送失败时预约已成功，无法回滚。 |
| **operatorId 硬编码 0** | `UserController.kh()` 调用 `bookMeeting` 时 `operatorId` 固定传 `0`，`hytz.hyztr` 始终为 0，无法追溯是谁发起的会议通知。 |

| 位置 | 值 | 业务含义 |

| `Hys.hyszt` | `"使用中"` | 会议室被预约后的状态（`bookMeeting` L141） |

| 返回 Map `msg` | 中文消息字符串 | 错误原因或成功提示 |

## 7. 数据模型

### hytz 会议通知/预约表

| 字段 | 类型 | 说明 |
|------|------|------|
| `hyId` | `INT AUTO_INCREMENT` | 主键 |
| `hynr` | `VARCHAR` | 会议内容 |
| `hyTime` | `DATETIME` | 通知创建时间 |
| `hydd` | `VARCHAR` | 会议地点（= `hys.hysbh` 会议室编号） |
| `hybtzr` | `INT` | 被通知人 userId |
| `hyztr` | `INT` | 操作人 userId |
| `ksTime` | `DATETIME` | 会议开始时间 |
| `jsTime` | `DATETIME` | 会议结束时间 |

### hys 会议室表

| 字段 | 类型 | 说明 |
|------|------|------|
| `hysbh` | `VARCHAR PK` | 会议室编号（如 A101, B202, C303） |
| `hyszt` | `VARCHAR` | 状态：`"空闲"` / `"使用中"` |
| `bz` | `VARCHAR` | 备注：`"已预约"` 等 |

> 注意：每个参会人对应一条 `hytz` 记录，N 个人参会会插入 N 条记录。会议室状态 `hys.hyszt` 的更新被 try-catch 包裹（L137-145），即使状态更新失败也不影响预约结果。
