# 会议室预定并发说明

> 本文档基于 `UserServiceImpl.bookMeeting`、`HytzMapper.xml` 及 `MeetingRoomBookingTest` 反推，说明并发预定的锁与事务设计。

---

## 1. 问题背景

会议室预定是典型的"检查后执行"（Check-Then-Act）场景：先查询目标时间段是否有冲突，再插入预定记录。如果两个线程同时通过了冲突检查，就会产生**双重预定（Double Booking）**。

这属于 **TOCTOU（Time-of-Check to Time-of-Use）** 竞态条件。

## 3. 锁设计详解

### 3.1 锁对象

```java
// UserServiceImpl.java:36
private final Object bookingLock = new Object();
```

- 类型：JVM 内置监视器锁（Intrinsic Lock / Monitor Lock）
- 作用域：`UserServiceImpl` 单例 Bean 的实例字段
- 生命周期：随 Spring 容器中该 Bean 的生命周期

### 3.2 为什么 synchronized 必须包裹在事务外层

```java
// UserServiceImpl.java:83-151
synchronized (bookingLock) {                    // ← 先拿锁
    TransactionTemplate txTemplate = ...;
    return txTemplate.execute(status -> {        // ← 再开事务
        // 检查冲突 + 插入记录
        ...
    });                                          // ← 事务提交
}                                                // ← 再释放锁
```

**关键原因**：如果将锁放在事务内部（或使用 `@Transactional` + `synchronized`），会出现以下竞态窗口：

```
时间线           线程 A                          线程 B
─────────────────────────────────────────────────────────
t1    开启事务
t2    获取锁
t3    检查冲突 → 无冲突
t4    INSERT 预定记录
t5    释放锁
t6                                        获取锁
t7                                        检查冲突 → 无冲突 ❌
t8                                        （A 的事务尚未提交，B 读不到 A 的 INSERT）
t9    事务提交
t10                                       INSERT 预定记录 → 双重预定！
t11                                       释放锁
t12                                       事务提交
```

而当前实现（`synchronized` 在事务外层）保证了：

```
时间线           线程 A                          线程 B
─────────────────────────────────────────────────────────
t1    获取锁
t2    开启事务
t3    检查冲突 → 无冲突
t4    INSERT 预定记录
t5    事务提交                              阻塞等待锁...
t6    释放锁
t7                                        获取锁
t8                                        开启事务
t9                                        检查冲突 → 发现冲突 ✓
t10                                       返回失败
t11                                       释放锁
```

### 3.3 参数校验在锁外执行

```java
// UserServiceImpl.java:78
validateBookingParams(hysbh, ksTime, jsTime, userIdList);
```

`validateBookingParams`（行 154-177）检查以下条件，不需要数据库访问，因此放在锁外以减少持锁时间：

| 校验项 | 失败消息 |
|--------|---------|
| 时间参数不能为 null | `"时间参数不能为空"` |
| 开始时间必须早于结束时间 | `"开始时间不能晚于或等于结束时间"` — 注意包含"等于" |
| 会议室编号不能为空 | `"会议室编号不能为空"` |
| 参会人列表不能为空 | `"参会人列表不能为空"` |

## 4. 冲突检测 SQL

### 4.1 会议室时间段冲突

```sql
-- HytzMapper.xml:14-19
SELECT COUNT(*) FROM hytz
WHERE hydd = #{hydd}           -- 同一会议室
  AND ksTime < #{jsTime}       -- 已有预定的开始时间 < 新预定的结束时间
  AND jsTime > #{ksTime}       -- 已有预定的结束时间 > 新预定的开始时间
```

这是标准的**半开区间重叠检测**算法：区间 `[A_start, A_end)` 与 `[B_start, B_end)` 重叠，当且仅当 `A_start < B_end AND A_end > B_start`。

```
示例 1: 冲突
已有预定:   |---- 09:00 ========== 10:30 ----|
新预定:            |---- 10:00 ========== 11:00 ----|
                               ↑ 重叠区间

示例 2: 不冲突（紧邻）
已有预定:   |---- 09:00 ========== 10:00 ----|
新预定:                                      |---- 10:00 ========== 11:00 ----|
                                              ↑ 严格不等式，10:00 = 10:00 不算重叠
```

> **设计决策**：紧邻的会议（一个 10:00 结束，下一个 10:00 开始）**不冲突**，这是半开区间 `[start, end)` 的特性。

### 4.2 参会人日程冲突

```sql
-- HytzMapper.xml:21-26
SELECT COUNT(*) FROM hytz
WHERE hybtzr = #{userId}       -- 同一参会人
  AND ksTime < #{jsTime}
  AND jsTime > #{ksTime}
```

对每个参会人逐一检查（`UserServiceImpl.java:110-119`），防止同一用户在不同会议室被重复预定。

### 4.3 冲突错误消息

| 冲突类型 | 消息 | 代码位置 |
|---------|------|---------|
| 会议室时间冲突 | `"会议室 {hysbh} 在该时间段已被预约"` | `UserServiceImpl.java:104` |
| 用户日程冲突 | `"用户 {userId} 在该时间段已有其他会议"` | `UserServiceImpl.java:114` |

## 5. 预定记录写入

每次预定按**每个参会人**插入一条 `hytz` 记录（`UserServiceImpl.java:123-134`）：

```
参会人列表 = [userId_1, userId_2, userId_3]
         │
         ▼  对每个 userId:
    INSERT INTO hytz (hynr, hyTime, hydd, hybtzr, hyztr, ksTime, jsTime)
    VALUES ('会议预约', NOW(), '会议室编号', 当前userId, 组织者userId, 开始时间, 结束时间)
```

之后更新会议室状态（`UserServiceImpl.java:137-145`）：

```sql
UPDATE hys SET hyszt = '使用中', bz = '已预约' WHERE hysbh = #{hysbh}
```

> 会议室状态更新失败被静默吞掉（catch 块仅 print），不影响预定成功。

## 6. 数据模型

### 6.1 hys（会议室）

| 字段 | 类型 | 说明 | 取值 |
|------|------|------|------|
| `hysbh` | VARCHAR | 会议室编号（自然主键） | 如 `"A101"`, `"B202"` |
| `hyszt` | VARCHAR | 会议室状态 | `"空闲"` / `"使用中"` |
| `bz` | VARCHAR | 备注 | `"小会议室"` / `"已预约"` |

### 6.2 hytz（会议预定/通知）

| 字段 | 类型 | 说明 |
|------|------|------|
| `hyId` | INT (PK, 自增) | 预定记录 ID |
| `hynr` | VARCHAR | 会议内容（固定写入 `"会议预约"`） |
| `hyTime` | DATETIME | 预定创建时间 |
| `hydd` | VARCHAR | 会议地点（= 会议室编号） |
| `hybtzr` | INT | 被通知人（参会人）用户 ID |
| `hyztr` | INT | 主体人（组织者）用户 ID |
| `ksTime` | DATETIME | 会议开始时间 |
| `jsTime` | DATETIME | 会议结束时间 |

> **注意**：`hytz` 表无唯一约束，不存在数据库级兜底防护。并发安全完全依赖应用层 `synchronized`。

## 8. 单 JVM 局限性

### 8.1 当前设计的适用范围

```
  ┌───────────────────────────────┐
  │         单 JVM 部署           │
  │                               │
  │  Thread A ──┐                 │
  │             ├── bookingLock ──│── 互斥有效 ✓
  │  Thread B ──┘                 │
  │                               │
  └───────────────────────────────┘
```

### 8.2 多实例部署时失效

```
  ┌──────────── JVM 1 ───────────┐    ┌──────────── JVM 2 ───────────┐
  │                               │    │                               │
  │  Thread A ── bookingLock_1    │    │  Thread C ── bookingLock_2    │
  │          ↕ 互斥               │    │          ↕ 互斥               │
  │  Thread B ── bookingLock_1    │    │  Thread D ── bookingLock_2    │
  │                               │    │                               │
  └───────────────────────────────┘    └───────────────────────────────┘
         ↑                                      ↑
         └──── 两个锁对象互不可见，无法互斥 ────┘
                          ↓
                    双重预定风险 ✗
```

### 8.3 多实例部署时的改进方向

| 方案 | 实现方式 | 复杂度 |
|------|---------|--------|
| **数据库行锁** | `SELECT ... FOR UPDATE` 锁定会议室行 | 低 |
| **唯一约束** | 在 `hytz` 表上建联合唯一索引 `(hydd, ksTime, jsTime)` 作为兜底 | 低 |
| **分布式锁** | Redis `SETNX` / ZooKeeper / etcd | 中 |
| **乐观锁** | 版本号字段 + 重试逻辑 | 中 |

> **当前状态**：`hytz` 表无任何唯一约束，`hys` 表无主键定义。数据库层面不存在任何防重复预定的兜底机制。如果计划水平扩展或负载均衡部署，必须在数据库层面补充约束。
